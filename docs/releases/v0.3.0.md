## Merx v0.3.0 — Verified payments and durable orders

Merx can now take real, verifiable payments while staying open source, provider-neutral and runnable offline. This release adds a payment state machine, signed payment confirmations, optional Stripe Checkout and GoPay adapters, and durable SQLite storage, still with **zero runtime dependencies**.

### Try it

```bash
git clone --branch v0.3.0 https://github.com/kamilkubik89/merx.git
cd merx
npm run demo:payments
```

The demo creates an order, opens a hosted checkout, rejects a forged webhook, accepts a signed one, deduplicates a replay and verifies the store-signed payment confirmation. It needs no account, API key or network access, and no money moves.

### Highlights

**Payment is verified, not assumed.**
The store-signed receipt still means *order accepted*. Settlement now has its own state machine (`requires_action → paid → partially_refunded → refunded`, plus `payment_failed`, `canceled` and `disputed`). A separate `merx-payment-confirmation/1` statement is signed only after a verified provider event or reconciliation. A browser redirect never marks an order paid.

**Optional provider adapters, no SDKs.**
- **Stripe Checkout:** hosted sessions built from server-side totals, idempotency keys, `Stripe-Signature` verification over the raw body, livemode and Connect checks, reconciliation, refunds and session expiry. Live keys are refused unless you opt in.
- **GoPay:** for Czech and Slovak merchants. Notifications are unsigned, so the adapter verifies every one through an authenticated status lookup. Sandbox by default.
- **Your provider:** implement `PaymentProvider` and opt into `verifyWebhook`, `getPaymentStatus` and `refund`. The engine applies the same deduplication, amount checks and transitions to every provider.

**Durable and recoverable.**
`SqliteStore` (built-in `node:sqlite`) persists orders, consumed mandate nonces, redeemed deals, stock deductions, payment attempts, processed webhook events and an audit trail. Mandate replays stay rejected after a restart. Missed webhooks are reconciled. Refunds and cancellations are authenticated admin operations.

**Agent-facing and access-controlled.**
`payment_status` and `payment_confirmation` work over REST, MCP and A2A. `place_order` returns a one-time order access token; Merx stores only its hash.

### Upgrade notes

- **No breaking API changes.** Existing providers that implement only `createPayment` keep working and are reported as `verifies_settlement: false`.
- Orders gain `payment.status`, `payment.verifies_settlement` and related fields. `order.status` is now derived from payment state and can be `refunded`.
- `place_order` responses include `access_token`. Store it with the order and send it as `Merx-Order-Token`.
- For any non-demo use, set `MERX_STORE=sqlite:<path>`. The default in-memory store forgets state on restart.
- Set `MERX_REQUIRE_ORDER_TOKEN=1` now. It is planned to become the default in 0.4.
- `SqliteStore` requires Node.js 22.13+. Everything else still runs on 22.6+.

### Quality

- 82 tests, all offline: forged and replayed webhooks, amount tampering, out-of-order events, expiry and retry, reconciliation, refunds, cancellation, restart durability, and concurrent duplicate submissions on one database.
- Provider APIs are replaced by local stand-ins. CI uses no credentials and makes no charges.
- 99% line coverage at release preparation.

### Limits

Merx is pre-1.0. SQLite covers single-node deployments; a PostgreSQL store for multiple instances is the next storage milestone. Disputes are tracked as a status but not automated. x402, AP2, UCP and ACP are still roadmap items, and the Merx mandate is not AP2. Merx is not affiliated with Stripe or GoPay. Using hosted payment pages keeps card data out of Merx, but the project makes no PCI DSS or regulatory compliance claim. Production readiness depends on your deployment, key management and review.
